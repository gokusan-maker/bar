# バー予約自動反映アプリ 要件定義書（ドラフト v0.1）

作成日: 2026-10-20
ステータス: たたき台（「9. 未決事項」の回答で確定させる）

---

## 1. 背景と目的

### 1.1 背景
- バーの予約はInstagram DM・LINE・X（旧Twitter）など複数のSNSで届き、店主が手作業で台帳やカレンダーに転記している。
- 営業中は返信・転記が遅れやすく、ダブルブッキングや記入漏れ、返信漏れが起きる。

### 1.2 目的
1. SNSで届いた予約メッセージを**自動で読み取り、予約として登録**する。
2. 登録した予約を**Googleカレンダーに自動で反映**し、店主・スタッフがいつものカレンダーで確認できるようにする。
3. 空き状況の確認からお客様への返信までを自動化し、**店主の手作業を減らす**。

### 1.3 成功指標（KPI案）
| 指標 | 目標 |
|---|---|
| 予約1件あたりの店主の作業時間 | 現状比 80% 削減 |
| SNS受信からカレンダー反映までの時間 | 1分以内（自動確定の場合） |
| ダブルブッキング件数 | 0件 |
| 予約メッセージの読み取り精度（日時・人数） | 95%以上（残りは店主確認に回す） |

## 2. スコープ

### 2.1 対象範囲（MVP）
- SNSからの予約メッセージ受信（優先チャネルは「9. 未決事項」で決定）
- メッセージから予約情報（日時・人数・名前・要望）を自動抽出
- 席・営業時間をもとにした空き判定
- 予約の確定 / 保留（店主確認待ち）/ お断り の判定とお客様への自動返信
- Googleカレンダーへの予約の登録・変更・削除の同期
- 店主向け管理画面（予約一覧・承認・手動編集・設定）

### 2.2 対象外（MVPでは扱わない）
- 事前決済・デポジット・キャンセル料の徴収
- POS・会計システム連携
- 顧客向けの独自予約サイト（※後続フェーズで検討）
- 多店舗管理

## 4. 業務フロー

### 4.1 新規予約（自動）
```
お客様がSNSでDM「10/25(土) 21時から2名でお願いします。山田」
   ↓ Webhookで受信
システムがメッセージを解析 → {日付:10/25, 時刻:21:00, 人数:2, 名前:山田}
   ↓
空き判定（営業時間・席数・既存予約・Googleカレンダーの予定）
   ├─ 空きあり & 自動確定条件を満たす → 予約確定
   │     → Googleカレンダーに登録
   │     → お客様へ確定メッセージを自動返信
   │     → 店主へ通知
   ├─ 情報が足りない（人数なし等） → お客様へ不足項目を自動で質問
   ├─ 判断があいまい / 大人数 / 貸切 → 「保留」として店主へ通知、承認後に確定
   └─ 満席 → 空いている近い時間帯を提案して返信
```

### 4.2 変更・キャンセル
- 同じSNSアカウントからの「変更」「キャンセル」メッセージを検知し、そのお客様の直近の予約に紐づける。
- 変更・キャンセルはGoogleカレンダーの該当予定も更新・削除する。
- 紐づけ先が複数あるなど判断できない場合は店主確認に回す。

### 4.3 店主による手動操作
- 電話・来店で受けた予約も管理画面から登録でき、同じくカレンダーに反映される。
- Googleカレンダー側で予定を移動・削除した場合はアプリ側にも反映する（双方向同期、「6.3」参照）。

### 4.4 リマインド
- 来店前日（または当日の指定時刻）に、お客様へSNSでリマインドを自動送信（ON/OFF設定可）。

## 5. 機能要件

### 5.1 SNS連携（受信・返信）
| ID | 要件 | 優先度 |
|---|---|---|
| F-SNS-01 | 対象SNSのDM/メッセージをWebhookでリアルタイム受信する | 必須 |
| F-SNS-02 | 受信メッセージを会話スレッド単位で保存する | 必須 |
| F-SNS-03 | 予約関連のメッセージかどうかを判定し、雑談・問い合わせは予約処理に回さない | 必須 |
| F-SNS-04 | お客様へ自動返信する（確定・質問・満席・リマインド） | 必須 |
| F-SNS-05 | 返信文テンプレートを店主が編集できる | 必須 |
| F-SNS-06 | 自動返信を止めて店主が手動で返信する「手動モード」に切り替えられる | 必須 |
| F-SNS-07 | 複数SNSを同じ予約台帳で一元管理する | 推奨 |

**SNSごとの連携方式（想定）**

| SNS | 方式 | 前提・制約 |
|---|---|---|
| LINE公式アカウント | Messaging API（Webhook） | 公式アカウント開設のみで利用可。無料枠の送信通数に上限あり（リマインド等の通数に注意）。**日本の店舗では最も実装しやすい** |
| Instagram | Meta Graph API（Instagram Messaging） | プロアカウント（ビジネス）＋Facebookページ連携が必要。Metaのアプリ審査が必要。お客様からの最後のメッセージから24時間以内しか返信できない制約あり |
| X（旧Twitter） | X API（DM） | DM APIの利用は有料プランが必要で、費用対効果が低い。MVPでは対象外を推奨 |
| Googleフォーム / 自前フォーム | プロフィールのリンクから誘導 | SNS APIが使えない場合の代替手段 |

### 5.2 予約情報の抽出（自動読み取り）
| ID | 要件 | 優先度 |
|---|---|---|
| F-AI-01 | 自然文から日付・時刻・人数・名前・要望（席の希望、誕生日等）を抽出する | 必須 |
| F-AI-02 | 「今週の土曜」「明日の9時」など相対表現を、受信日時と店の営業時間をもとに具体的な日時に変換する（例: 「9時」は営業時間から21時と解釈） | 必須 |
| F-AI-03 | 日付をまたぐ営業（例: 25:00＝翌1:00）を正しく扱う | 必須 |
| F-AI-04 | 抽出結果に確信度を付け、低い場合は店主確認（保留）に回す | 必須 |
| F-AI-05 | 足りない項目があればお客様に聞き返し、会話の流れを踏まえて予約を完成させる | 必須 |
| F-AI-06 | 新規予約・変更・キャンセル・問い合わせを区別する | 必須 |

※ 抽出にはLLM（Claude API等）を利用する想定。誤読のリスクがあるため、**確定前に必ず空き判定・ルールチェックを通す**。

### 5.3 予約管理・空き判定
| ID | 要件 | 優先度 |
|---|---|---|
| F-RSV-01 | 予約のステータスを管理する: 仮受付 / 保留（店主確認待ち）/ 確定 / 変更済 / キャンセル / 来店 / 無断キャンセル | 必須 |
| F-RSV-02 | 営業日・営業時間・定休日・臨時休業を設定できる | 必須 |
| F-RSV-03 | 席（カウンター○席、テーブル○卓など）と最大受付人数を設定できる | 必須 |
| F-RSV-04 | 1予約の標準滞在時間（例: 2時間）を設定し、重なりで空きを計算する | 必須 |
| F-RSV-05 | 自動確定の条件を設定できる（例: ○名以下、○日前まで、貸切は除く） | 必須 |
| F-RSV-06 | 満席時に近い空き時間帯を提案する | 推奨 |
| F-RSV-07 | 同時に届いた予約で同じ席を取り合った場合に、ダブルブッキングしない（排他制御） | 必須 |
| F-RSV-08 | 貸切予約の受付（店主承認必須） | 推奨 |

### 5.4 Googleカレンダー連携
| ID | 要件 | 優先度 |
|---|---|---|
| F-CAL-01 | 店主のGoogleアカウントでOAuth認証し、予約用カレンダーを選択（または新規作成）する | 必須 |
| F-CAL-02 | 予約確定時にカレンダーへ予定を作成する（件名例: 「【予約】山田様 2名」、説明欄にSNS・要望・管理画面URL） | 必須 |
| F-CAL-03 | 予約の変更・キャンセル時に予定を更新・削除する | 必須 |

| F-CAL-05 | カレンダー側での変更（時間移動・削除）を検知してアプリ側に反映する（Push通知＋差分同期） | 推奨 |
| F-CAL-06 | 店主の私用予定・臨時休業の予定を読み取り、その時間を受付不可にする | 推奨 |
| F-CAL-07 | 同期に失敗した場合は自動で再試行し、続けて失敗したら店主に通知する | 必須 |

## 6. 非機能要件

### 6.1 性能・可用性
- Webhook受信から自動返信まで: 原則30秒以内（LLM解析を含む）
- 稼働率: 99.5%以上（営業時間帯の夕方〜深夜を重視）
- 同時受信: 1店舗で同時に数十件程度を想定

### 6.2 セキュリティ・個人情報
- お客様の名前・SNSアカウント・会話内容は個人情報として扱い、通信・保存とも暗号化する。
- SNS・GoogleのアクセストークンはDBに暗号化して保存し、画面やログに出さない。
- 管理画面は店主・スタッフのみアクセス可（権限: 店主＝全操作、スタッフ＝閲覧・来店チェック）。
- Webhookは各SNSの署名を検証し、なりすましリクエストを拒否する。
- 個人情報の保存期間を設定する（例: 最終来店から2年で自動削除、要確認）。
- プライバシーポリシーを用意し、SNSプロフィールや自動返信で案内する（Metaのアプリ審査でも必須）。

### 6.3 データ整合性
- **正となるデータはアプリのDB**とし、Googleカレンダーは表示・共有用の写しとする。
- カレンダー側の変更は取り込むが、アプリとカレンダーで同時に変更された場合はアプリ側を優先し、店主に通知する。
- カレンダーの予定にはアプリの予約IDを埋め込み、対応関係を保持する。

### 6.4 運用・保守
- 全ての自動処理（受信・解析結果・返信・同期）を履歴として残し、後から追えるようにする。
- SNS APIの仕様変更・トークン失効を検知したら店主に通知する。

## 7. システム構成（案）

既存リポジトリと同じ **Next.js（TypeScript）** をベースにし、Vercelにデプロイする構成を想定。

```
[LINE / Instagram]  --Webhook-->  [Next.js API Routes (Vercel)]
                                        │
                                        ├─ メッセージ解析（Claude API）
                                        ├─ 予約ロジック・空き判定
                                        ├─ DB（Supabase / PostgreSQL）
                                        ├─ Google Calendar API
                                        └─ 返信・通知（各SNS API）
[店主のスマホ] --ブラウザ--> [管理画面（Next.js）]
```

| 項目 | 候補 |
|---|---|
| フロント / API | Next.js（App Router）、Vercel |
| DB・認証 | Supabase（PostgreSQL＋Auth） |
| 予約情報の抽出 | Claude API（構造化出力で日時・人数等をJSON化） |
| カレンダー | Google Calendar API（OAuth 2.0、Push通知） |
| 定期処理（リマインド・同期の再試行） | Vercel Cron |

### 7.1 主要データ（概要）
| テーブル | 主な項目 |
|---|---|
| shops（店舗） | 店名、営業時間、定休日、標準滞在時間、自動確定条件 |
| seats（席） | 種別（カウンター/テーブル）、定員 |
| customers（顧客） | 名前、SNS種別、SNSユーザーID、メモ、来店回数 |
| reservations（予約） | 顧客、日時開始・終了、人数、席、ステータス、要望、元メッセージ、GoogleカレンダーイベントID |
| messages（メッセージ） | SNS種別、方向（受信/送信）、本文、受信日時、解析結果、確信度 |
| integrations（連携設定） | SNS・Googleの接続情報（暗号化トークン） |
| audit_logs（操作履歴） | 誰が/システムが、何を、いつ |

## 9. 未決事項（確認したいこと）

1. **どのSNSで予約を受けていますか？**（Instagram / LINE / X / その他）最も件数が多いものを最初に対応します。
2. **自動確定の範囲**: 空いていれば全部自動確定で良いか、それとも全件店主の承認を挟みたいか。人数の上限（例: 5名以上は確認）や貸切の扱い。
3. **席の構成と営業時間**: カウンター何席・テーブル何卓か、営業時間、ラストオーダー、標準の滞在時間（時間制か、時間無制限か）。
4. **Googleカレンダーの使い方**: 既存の店のカレンダーに入れるか、予約専用カレンダーを作るか。スタッフにも共有するか。カレンダー上で直接予定を動かすことはあるか（双方向同期の要否）。
5. **お客様から取得したい情報**: 名前・人数・日時以外に必要なもの（電話番号、ダーツ利用の有無、誕生日など）。
6. **店主への通知手段**: LINE・メール・アプリのどれが良いか。
7. **キャンセルポリシー・無断キャンセル対策**: リマインドの要否、無断キャンセル常習者のブロック機能の要否。
8. **予算・運用費の許容範囲**: SNS API（LINEの有料プラン、XのAPI等）、サーバー・AI利用料の月額目安。
9. **ダーツとの関係**: ダーツマシンの台数単位で予約を受けるか（席予約とは別にダーツ台の予約が必要か）。

## 10. 実装状況（Phase 1 / 2026-10-20）

実装はこのリポジトリ（[README](../README.md)）。未決事項は以下の仮定で進め、すべて管理画面の設定で変更できるようにした。

| 未決事項 | 仮の決定 |
|---|---|
| 1. SNS | **LINEがメイン**、Instagram と X（Twitter）がサブ（2026-10-21 確定）。LINE・Instagram はメッセージを自動受付。X は X API が従量課金のため DM 連携はせず、X用の予約リンク（`/reserve?from=x`）で受け付けて「X」として集計 |
| 2. 自動確定 | 空きがあり4名以下なら自動確定。5名以上・貸切・読み取りに自信がないものは承認待ち（設定で全件承認にも切替可） |
| 3. 席・営業時間 | 19:00〜26:00、最終入店は閉店60分前、同時12名、滞在2時間（設定で変更） |
| 4. カレンダー | 店主が選んだカレンダーに書き込み。アプリ→カレンダーの片方向＋カレンダー上の休業・貸切予定の読み取り |
| 5. 取得項目 | 日時・人数・名前・要望のみ |
| 6. 店主への通知 | LINE（店主が公式アカウントを友だち追加） |
| 7. キャンセル対策 | 前日リマインドあり、ブロック機能なし |
| 9. ダーツ台 | 席予約のみ（台ごとの予約なし） |

要件との差分:
- 管理画面のログインはGoogleアカウントではなくパスワード方式（F-ADM-01）。店主用とスタッフ用（閲覧・来店チェックのみ）の2種類。
- カレンダー側での予定の移動・削除の反映（F-CAL-05）は、Push通知ではなく毎日17時の取り込み＋手動ボタンで実装（Vercelの無料プランではcronが1日1回のため）。
- 空き判定は席の割り当てではなく、同時人数の上限で行う。
- 集計（F-ADM-09）・操作履歴・個人情報の自動削除（初期値24か月、売上金額と証拠は帳簿として保存）は実装済み。

### 追加要件（2026-10-20）: 売上・バック・証拠写真
| ID | 要件 | 状況 |
|---|---|---|
| F-SALE-01 | 来店ごとに売上（お酒・料金・サービス料）を記録。予約から開くと人数×チャージ・サービス料を自動入力 | 実装済み |
| F-SALE-02 | 売上に証拠（伝票・レシートの写真、PDF）を複数添付。管理者だけが閲覧できる | 実装済み |
| F-SALE-03 | スタッフごとのバック率（お酒・料金・サービス料の%と1組あたりの固定額）を設定 | 実装済み |
| F-SALE-04 | 月ごとにSNS経由の売上とスタッフ別バックを集計し、CSVで出力 | 実装済み |
| F-SHOP-01 | 店の種類・席の構成（エリア名と席数）・チャージ額・サービス料率・バック対象を店主が設定 | 実装済み |

仮の決定: 「バック」は担当スタッフへの歩合として実装。担当はお客様ごとに設定し、売上入力時に変更できる。消費税の計算・POS連携は対象外。

## 11. 用語
| 用語 | 意味 |
|---|---|
| Webhook | SNSに新しいメッセージが届いた瞬間にアプリへ通知が飛ぶ仕組み |
| OAuth | 店主のGoogleアカウントでログインし、アプリにカレンダー操作の許可を与える仕組み |
| 保留 | 自動で確定せず、店主の承認を待っている予約 |
| 双方向同期 | アプリの変更をカレンダーへ、カレンダーの変更をアプリへ、の両方向で反映すること |
